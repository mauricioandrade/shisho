# ADR 0017 — Projetos em Java 17

- **Status:** aceito
- **Data:** 2026-10-18
- **Fase:** 17 (Java 17)

## Contexto

Na calibração com projetos reais ([ADR 0016](0016-real-projects.md)), quase todos foram recusados:
o spring-petclinic, o buckpal e os quickstarts do Quarkus declaram Java 17, e o Shishō só
analisava a partir do 21. Para analisá-los, a versão foi trocada numa cópia. A trava protegia
pouco: nenhuma kata de Spring depende de recurso do 21, e o mecanismo para lidar com versões mais
antigas já existia. Uma kata com `minJavaVersion` acima da versão do projeto vira INFO ("ao migrar
para o X…"), e é assim que a `prefer-scoped-values` se comporta num projeto 21.

O que prendia o Shishō no 21 era uma constante com dois papéis. `JavaVersion.BASELINE` era ao
mesmo tempo a versão mais antiga aceita e a versão assumida quando o build não declara nenhuma, e
servia ainda de `minJavaVersion` para quase toda kata. Baixar a constante para 17 mudaria também
o que se assume num build sem versão.

## Decisão

`BASELINE` deu lugar a duas constantes, cada uma com um papel:

| Constante | Valor | Papel |
|---|---|---|
| `JavaVersion.MINIMUM` | 17 | a versão mais antiga analisada; o `minJavaVersion` de uma kata que não depende de recurso da linguagem |
| `JavaVersion.ASSUMED` | 21 | a versão assumida quando o build não declara nenhuma |

O 17 foi escolhido por ser LTS e o mínimo do Spring Boot 3 e do Quarkus 3, as versões que o
Shishō conhece. Records, sealed e o `instanceof` com padrão já existem nele, então as katas que
sugerem record (`dto-not-record`, `configuration-properties-not-record`) valem sem mudança. O
`ASSUMED` continua 21: um build sem versão costuma ser um projeto novo ou herdar a versão de um
parent remoto, e assumir a LTS mais antiga faria toda sugestão do 21 virar "ao migrar".

Num projeto 17, a `prefer-virtual-threads` passa a aparecer como sugestão de migração, sem tirar
nota. Para quem está no 17, é exatamente a lição que interessa.

Dois testes guardam a decisão:

- `katasWithoutAJavaFeatureRunOnEveryAnalyzedVersion`: uma kata sem recurso associado declara
  `MINIMUM`. Se alguém voltar a usar a versão assumida como mínimo, o teste quebra.
- `theGeneratedCrudCompilesOnTheMinimumJava`: o `shisho crud` de cada template, num projeto 17, é
  lido no nível de linguagem do 17 e não recebe nenhuma lição. Os templates usam `Stream.toList()`
  (Java 16) e records, nada do 21.

## Alternativas registradas

- **Baixar direto para o 11 (ou o 8).** É onde mora o código legado, e as lições de migração
  ("ao migrar para o 17, este DTO vira record") seriam úteis. Mas abaixo do 17 o projeto quase
  sempre é Spring Boot 2, com `javax.*`, e o Shishō gera código `jakarta.*`: o `@Valid` que o
  `shisho fix` importa e os templates do `shisho crud` não compilariam lá, e a lição da
  `missing-controller-advice` recomenda `ProblemDetail`, que só existe no Spring 6. Fica para um
  passo próprio.
- **Assumir 17 quando o build não declara versão**, já que é o mínimo. O Shishō erraria para baixo
  em quase todo projeto novo, e as sugestões do 21 deixariam de ser cobradas justo onde estão
  disponíveis.

O que continua de fora: projetos Spring Boot 2.7 em Java 17 são analisados, mas o Shishō ainda
supõe `jakarta.*` no que gera e no que recomenda. Isso não é novo, porque o Boot 2.7 também roda
no 21, mas fica mais provável agora. Nos projetos reais em Java 17 da calibração, todos já usam
`jakarta.*`.

## 📚 Estudo — LTS e a versão de uma constante

O Java sai a cada seis meses, e de dois em dois anos uma versão é **LTS** (*long-term support*):
8, 11, 17, 21, 25. As empresas ficam nas LTS, então é nelas que mora quase todo projeto real. O 17
é a LTS em que o ecossistema Spring "virou a página": o Spring Boot 3 exige 17 e trocou `javax.*`
por `jakarta.*`. Por isso ele é um bom piso: abaixo dele, o problema não é a versão da linguagem,
é outro framework.

A outra lição é sobre constantes. Um nome como `BASELINE` parece uma coisa só, mas aqui servia a
três perguntas: "qual a versão mais antiga aceita?", "o que assumir quando ninguém diz?" e "a
partir de quando esta kata vale?". Enquanto as três respostas eram 21, ninguém notava. Quando uma
delas precisou mudar, a constante teve de ser separada em duas. Uma constante com um nome
genérico e vários usos é um acoplamento escondido: mudar o valor muda comportamentos que não têm
nada a ver um com o outro.
